# 공통 Worktree 작업 구성 기준

프로젝트별 합의가 우선한다. 기존 설정과 실제 작업 ID는 CLI로 확인하고, 데이터 변경도 CLI로 한다. 저장 충돌이 나면 최신 상태를 읽고 변경을 다시 판단한다. 신규 프로젝트는 필수 설정을 확인한 뒤 초기화한다.

## 마일스톤과 작업

- 마일스톤은 완료 후 사용할 수 있는 결과와 완료 기준으로 정의한다. 구성 요소가 연결된 실제 사용 흐름까지 확인한다.
- 작업은 독립적으로 검증할 수 있는 결과 단위로 등록한다. 같은 목적의 수정·조사·테스트·문서 갱신은 기존 작업에 묶는다.
- 작업에는 제목, 목적, 범위, 완료 조건, 검증 방법과 필요한 분류·참조를 적는다. 의존성은 실제 선행 결과가 필요할 때만 설정한다.
- 설명은 작업에 필요한 기준만, 댓글은 새 결정·차단·검증 결과만 간결하게 적는다. 상세 내용은 링크하고 기존 내용을 반복하지 않는다.
- 구성안 검토만 요청받았으면 등록하지 않는다. 등록 요청을 받으면 중복을 확인하고 합의한 범위만 반영한다. 담당자는 합의한 책임 주체를 지정한다.

## 착수와 완료

- 등록 시 날짜는 비워 둔다. 실제 착수해 `doing`으로 바꿀 때 프로젝트 시간대 기준으로 시작일과 예정 종료일을 지정한다. 실제 완료가 늦으면 종료일을 실제 완료일로 갱신한다. 예상 작업시간은 쓰지 않고, 마일스톤 일정은 별도 합의가 있을 때만 지정한다.
- 완료 순서는 **구현 → 자체 검증 → 사용자 확인·승인 → `done`**이다. 승인 전에는 `doing`을 유지하고 댓글에 검증 결과, 남은 제약, 확인 방법을 남긴다. 중요한 결정과 차단 원인·해제 조건도 댓글에 기록한다.
- 승인 대기 작업에 의존하는 후속 작업은 기본적으로 대기한다. 사용자가 연속 구현을 허용했고 선행 결과를 검증했으며 Worktree가 착수를 허용할 때는, 승인 대기 의존성을 댓글에 기록하고 진행할 수 있다. 의존성을 우회하거나 승인 전에 `done`으로 바꾸지 않는다. 선행 결과가 바뀌면 영향을 받은 작업을 다시 검증하고, 연결된 결과는 통합 검증한다.

## 변경 요청

- 승인 전 기존 완료 조건을 충족하기 위한 수정은 같은 작업에서 처리한다. 독립적인 기능·개선은 새 작업으로 분리한다.
- 완료 후 발견한 오류는 `bug`, 사용성·성능 개선은 `improvement`로 등록한다. 원래 작업을 참조하고, 마일스톤이 이미 완료됐다면 다음 개선·패치 마일스톤에 배치한다.
